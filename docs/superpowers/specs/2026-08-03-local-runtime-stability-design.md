# 第五阶段：本机稳定运行设计

## 一、目标

第五阶段把现有本地工作台从“能启动”提升为“可判断、可停止、可复用、出错可定位”。用户仍通过根目录批处理文件操作，不需要理解 Python、Node.js、Uvicorn 或 Next.js 命令。

本阶段不修改分析内核、后端业务接口、数据库结构或报告方法论。后端只使用现有 `GET /health` 健康检查。

## 二、方案选择

采用生产模式本地运行：FastAPI 继续监听 `127.0.0.1:8000`，Next.js 使用 `next start` 监听 `127.0.0.1:3000`。PowerShell 负责环境检查、构建判断、进程启动、端口归属、健康检查、状态记录与停止；`start.bat`、`stop.bat`、`status.bat` 仅作为双击入口。

不采用继续运行 `next dev` 的方案，因为开发模式会在启动期间改写构建缓存，并且更容易残留热更新进程。不安装 Windows 服务，因为当前是本机单用户自用，服务安装、管理员权限和卸载维护超出必要范围。

## 三、运行边界

1. 前端固定使用 `127.0.0.1:3000`，后端固定使用 `127.0.0.1:8000`。
2. 端口空闲时启动对应服务。
3. 端口已被本仓库进程监听且健康时复用，不重复启动。
4. 端口被其他程序占用时立即停止并显示进程信息，不杀死未知进程。
5. 停止时再次核对 PID 与命令行归属，只终止本仓库的监听进程。
6. 只有前后端健康检查全部通过后才打开浏览器。
7. PID、状态与日志写入根目录 `.runtime/`，该目录不进入 Git。

## 四、启动流程

```text
双击 start.bat
  -> 解析仓库绝对路径
  -> 检查 PowerShell、Python、Node、npm 与前端依赖
  -> 检查 8000 / 3000 端口归属
  -> 前端构建不存在或比源码旧时执行 npm run build
  -> 启动缺失的 FastAPI / Next.js 生产服务
  -> 轮询 /health 与前端首页
  -> 记录实际监听 PID 和状态
  -> 两端都健康后打开浏览器
```

前端构建新鲜度由 `.next/BUILD_ID` 与 `src/`、`public/`、`package.json`、`package-lock.json`、`next.config.ts`、`tsconfig.json` 的最新修改时间比较决定。缺少依赖时给出明确安装命令，不静默联网安装。

## 五、停止与状态

- `stop.bat`：读取实时端口监听者，验证其命令行属于当前仓库后停止；状态文件只能提供线索，不能绕过归属验证。
- `status.bat`：显示前端和后端的端口、PID、归属与健康状态，并给出日志目录。
- 状态文件采用 JSON，只保存仓库路径、端口、PID 和更新时间，不保存密钥或业务数据。

## 六、错误处理

- 环境缺失：显示缺少的命令或目录以及修复方法。
- 构建失败：保留构建输出，停止启动流程，不启动旧前端。
- 健康检查超时：显示对应服务日志位置并返回非零退出码。
- 端口冲突：显示端口、PID 和进程命令行，不自动换端口，避免前后端 CORS 与固定 API 地址失配。
- 部分启动成功：保留已经健康的本项目服务，报告失败项；用户可运行 `stop.bat` 清理。

## 七、测试与验收

1. PowerShell 纯函数测试覆盖路径归属、端口决策和构建新鲜度。
2. 启动烟雾测试验证两个端口均只存在一个监听者、`/health` 和首页返回成功。
3. 重复执行启动器验证复用而非重复启动。
4. 状态命令验证能够识别运行状态。
5. 停止命令验证两个端口释放，随后重新启动供用户使用。
6. 前端 41 项测试、TypeScript 检查和 Next.js 生产构建继续通过。
7. 最后执行整个仓库的结构、Git、测试与运行风险检查。

## 八、非本阶段范围

- Windows 服务安装、开机自启、系统托盘和自动更新。
- Docker、远程部署、局域网开放和公网访问。
- 用户系统、收费系统、云同步和多用户隔离。
- 修改后端业务 API、任务队列、分析内核或 PDF 转换实现。
