# 报告补证与分析流水线提速设计

## 一、目标

在不降低报告写作质量和证据约束的前提下，缩短联网分析耗时，并为每份报告提供版本化的证据补充能力。用户可以选择本地材料、重新联网调查或二者结合，AI 处理后的结果必须保存为同一报告的新版本，原版本不可覆盖。

## 二、已确认瓶颈

- 最近一份真实联网报告耗时 282.7 秒。
- DuckDuckGo 超时且零结果后，主查询和历史对照查询仍串行执行同类重试。
- 零有效来源时，系统仍发起第二次 LLM 证据账本提取，最终研究状态仍为 fallback。
- Word/PDF 导出约 10 秒，不是主瓶颈。

## 三、性能策略

1. 主查询与历史对照查询最多两路并行执行。
2. 网页正文最多四路并行抓取，返回顺序与输入 URL 顺序一致。
3. 主查询因检索源不可用而零结果时，不再对同一提供方执行历史查询。
4. 证据来源目录为空时，直接建立透明的本地降级账本，不调用证据提取 LLM。
5. 记录 search、fetch、generate、research、export 和 total 的真实耗时，随任务结果保存。
6. 成功任务不改变现有报告内容、质量闸门和正式导出行为。

## 四、报告补证入口

每份报告顶部和证据不足提示区提供“补充信息与证据”入口。面板包含：

- 补充目标：默认带入当前资料缺口，允许用户说明要核验的判断、主体、关系或时间范围。
- 本地材料：上传新材料或选用已有材料。
- 重新联网：重新检索公开来源。
- 混合模式：本地材料与联网检索可以同时启用。
- 人工编辑：保留现有“编辑版本”入口。

## 五、后台任务与版本语义

新增报告补证任务，复用现有 Task 队列、WebSocket 进度和报告生成器：

- Task 增加 operation、target_task_id、base_version_id，用于区分普通分析和 evidence_enrichment。
- POST `/api/reports/{task_id}/enrichments` 创建后台任务并返回 job_task_id。
- 补证任务锁定启动时的基础版本，读取其 Markdown 和研究快照。
- 没有找到新增材料或公开来源时，任务以 no_evidence 状态结束，不调用 LLM、不创建空版本。
- 找到有效证据后，AI 只更新受影响的事实、判断、来源、关系和资料缺口，随后重新校验、生成研究账本和正式产物。
- 新版本 kind=`enriched`、edited_by=`ai`，版本摘要标注材料补充、联网补充或混合补充。
- 若任务完成时当前版本仍是 base_version_id，新版本自动设为当前；若当前版本已变化，新版本保存为非当前候选，避免覆盖并发人工修改。

## 六、错误与可信度

- 未配置用户自己的 AI API 时禁止启动 AI 补证，并引导前往设置。
- 联网失败必须保留降级原因，不得伪造来源。
- 新来源与旧来源按规范化 URL 去重，转载来源仍按现有研究账本规则折叠。
- 补证前后变化使用现有 research_changes 机制展示，不另造差异系统。
- 补证失败不修改原报告及其当前版本。

## 七、前端交互

- 报告顶部新增“补充证据”命令。
- 证据不足警告区提供同一入口。
- 对话框使用来源复选项、材料选择、补充目标文本框和明确的 API 使用提示。
- 提交后显示后台任务进度，并允许进入现有分析任务页查看完整阶段。
- 完成后刷新报告，自动选中新版本；并发冲突时提示候选版本未自动设为当前。

## 八、验收标准

- 零来源分析只调用一次正文 LLM，不调用证据账本 LLM。
- 同一提供方主检索失败时不会执行第二个无效历史查询。
- 多 URL 抓取并行且输出顺序稳定。
- 材料、联网、混合三种补证均可生成同报告新版本。
- 零新增证据不创建版本。
- 基础版本变化时不覆盖当前版本。
- 任务结果可读取阶段耗时。
- 后端核心测试、前端测试和 Next.js 构建全部通过。
