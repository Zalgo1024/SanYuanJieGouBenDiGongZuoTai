# 证据—判断账本纵切设计

**日期：** 2026-08-16  
**状态：** 已批准方向的第一阶段实现规格

## 一、目标

在不推翻现有报告工作流和前端的前提下，为每次分析同时生成一份机器可校验的“研究账本”。报告仍然是主要阅读载体，但关键判断、关系边、资料来源和信息缺口不再只存在于自然语言中。

第一阶段完成后，用户应当能够：

- 点击关键判断，查看支撑证据、反对证据、来源类型、发布时间和原文摘录；
- 区分事实、来源观点、系统推断和用户输入；
- 查看判断的高 / 中 / 低置信度及原因；
- 在关系图谱中点击一条边，回答“系统为什么认为 A 与 B 存在这条关系”；
- 查看当前仍无法确定的问题以及最值得补充的材料；
- 在切换报告版本时看到与该版本绑定的研究快照，而不是串用其他版本的证据。

## 二、方案选择

### 方案 A：只把研究数据放进 `Task.result`

改动最小，但无法可靠绑定报告版本。人工修订、AI 再改和回滚后容易出现正文与证据错配。

### 方案 B：立即建立来源、判断、关系和绑定的完整关系型表

长期查询能力最好，但第一阶段会引入较大的迁移、并发和编辑成本，也容易再次把项目做成一套复杂平台。

### 方案 C：版本化 JSON 研究快照

在 `Task.result` 中保存当前研究账本，同时给 `ReportVersion` 增加独立的 `research_snapshot`。使用 Pydantic 契约和确定性校验保证结构可靠，API 与前端只读取经过校验的对象。未来需要跨项目统计、持续监测时，再把稳定字段迁移为关系型表。

**本阶段采用方案 C。** 它能完整打通生成、存储、版本、API 和前端，又不改变现有报告生成主链。

## 三、研究账本契约

研究账本使用 `schema_version = "1.0"`，包含五类对象。

### 1. 来源 `sources`

- `id`：账本内稳定 ID；
- `title`、`url`、`excerpt`；
- `source_type`：官方文件、公司公告、主流媒体、自媒体、论坛、社交媒体、用户材料或未知；
- `source_level`：原始来源、二手来源、三手转述或用户提供；
- `published_at`、`retrieved_at`；
- `independence_group`：转载或同源内容归为同一证据组；
- `material_id`：能对应本地材料时记录。

### 2. 判断 `claims`

- `id`、`text`、`section`；
- `claim_type`：`fact` / `source_view` / `inference` / `user_input`；
- `significance`：关键判断或支撑判断；
- `confidence`：高 / 中 / 低 / 未知，不生成虚构百分比；
- `confidence_reasons`；
- `evidence_ids`、`counter_evidence_ids`；
- `unsupported`：是否缺少足以支撑当前表述的证据。

### 3. 关系 `relations`

- `id`、`source_node`、`target_node`、`label`；
- `relation_type`、`direction`、`polarity`；
- `confidence`、`evidence_ids`、`claim_id`；
- `status`：确认、推测或冲突。

### 4. 资料缺口 `gaps`

- `id`、`question`、`reason`；
- `impact`：该缺口会影响哪些判断；
- `recommended_materials`：下一轮最值得补充的材料。

### 5. 可解释质量指标 `metrics`

- 关键判断证据覆盖率；
- 有直接来源的事实比例；
- 独立来源组数量；
- 未证实推断数量；
- 冲突证据数量；
- 资料缺口数量。

这些指标只描述资料与推断可靠性，不评价文笔，也不输出笼统的“质量 100 分”。

## 四、生成与校验流程

现有 Markdown 报告仍由当前工作流生成。报告完成后增加一个有边界的结构化提取步骤：输入最终 Markdown 和已编号的来源清单，要求 LLM 只返回研究账本 JSON。

确定性校验器负责：

1. 清理未知字段并保证 ID 唯一；
2. 拒绝引用不存在来源的证据 ID；
3. 将无证据的“事实”降级为低置信度系统推断并标记 `unsupported`；
4. 对同源转载按 `independence_group` 去重；
5. 关系边缺少证据时只能进入“推测”层，不能伪装成确认事实；
6. 自动计算可解释质量指标；
7. 提取失败时生成最小降级账本，报告任务本身仍可完成。

规则引擎模式不伪造来源：用户正文只标为 `user_input`，报告中的关系默认标为推测，直到找到外部证据。

## 五、版本与 API

- `Task.result.research` 保存当前任务研究账本；
- `ReportVersion.research_snapshot` 保存对应版本快照；
- `ReportVersion.research_status` 为 `verified`、`fallback`、`stale` 或 `unavailable`；`fallback` 表示系统只保留了可确认的输入、来源目录和低置信度关系，不能冒充已经完成逐条核验；
- 原始版本播种时复制任务当前账本；
- 人工修订与 AI 再改默认继承上一版快照但标为 `stale`，明确提示正文已变化、绑定待复核；
- 回滚时同时恢复该版本的 Markdown 与研究快照。

新增读取接口：

`GET /api/reports/{task_id}/research?version_id={version_id}`

接口返回目标版本的账本和状态。单个版本详情也返回 `research` 与 `research_status`，减少前端切换版本时的竞态。

## 六、前端交互

保留现有报告页面、关系图谱页面和整体视觉语言，只增加两处研究交互。

### 报告页

在正文之前增加紧凑的“关键判断”区域。每条判断显示类型、置信度、证据数量和不确定性原因。点击后打开证据详情，展示来源、摘录、日期、等级、支持或反对关系以及资料缺口。

### 关系图谱页

关系边优先按 `claim_id` 或关系 ID 匹配研究账本。选中边后显示对应证据和置信度。旧报告没有映射时继续使用现有报告级来源，并明确标注为“未建立边级绑定”。

## 七、失败与兼容策略

- 研究账本失败不阻塞 Word、PDF 和 Markdown 交付；
- 历史报告没有账本时返回 `unavailable`，前端显示兼容提示；
- 人工修订后的继承快照必须显示 `stale`，不得暗示已经重新核验；
- 所有新增数据库字段通过现有幂等 SQLite 迁移方式加入；
- 不修改现有三元理论配置、章节路由和报告渲染规则。

## 八、本阶段不做

- 不实现持续抓取、定时监测和跨版本自动差异分析；
- 不实现情景概率模型、A/B/C 行动方案和决策角色表单；
- 不把 JSON 快照提前拆成复杂关系型知识库；
- 不重写现有前端，不新增独立一级菜单；
- 不用 LLM 编造概率、来源质量分或关系强度。

后续 P0 将在本账本上继续增加非显然发现、条件预测和可执行方案；P1 的时间追踪和持续监测也以该契约为输入，而不是继续解析散文报告。
