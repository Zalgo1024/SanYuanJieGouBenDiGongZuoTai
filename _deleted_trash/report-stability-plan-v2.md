# 报告稳定性改进方案 v2（真正抓重点）

> 用户原话：不是在改细节就是在改出报告的规则，但就是无法撰写一份稳定的报告，之前的改进一直抓不住重点（哪怕是 codex 2.6 也没用）。
> 结论：之前所有方案（含我上一版 v1、codex 的 spec 注入 + contract 后校验）都优化错了层。

---

## 一、先承认：之前为什么都没抓住重点

上一版（v1）给的是"焊死结构 + 降级链 + 回归测试"，codex 落地了 spec 注入 + contract 后校验 + AI 味拦截。你试了还是不稳。原因现在看很清楚：

**这些全在优化"怎么约束一个会漂移的生成器"，但没解决"内容到底从哪来、能不能复现"。**

只要最终喂给内核 `export_from_text()` 的那份分析 Markdown 是**某次运行时实时生成的**（LLM 采样有随机性、联网素材每次不同、重试会换结果），它就不可能稳定。把 spec 塞进 prompt、加再多 contract 拦截，只是让"坏报告"少一点，不是让"好报告"可复现。

> **稳定 = 同一份输入永远得到同一份输出。只要内容靠实时生成，这条就永远不成立。**

---

## 二、根因诊断

项目把两件性质完全不同的事混进了一条实时流水线：

1. **写分析**（创作内容）——非确定性，依赖人或模型临场发挥。
2. **出格式**（渲染排版）——`export_from_text()` 是纯函数，输入固定 → 输出固定，本该是稳定基石。

问题出在：流水线在调用渲染**之前**，先实时"造"出那份 Markdown。这一步非确定性，且**每次运行都重造**。所以你每次点"生成"拿到的是不同东西。

**反例对照**：原始 CLI（`cases/run_*.py`）为什么稳？因为它的 Markdown 是**写死在代码里的常量**，永不重造，渲染只是纯函数。Web 平台把"实时生成"替换了"写死的常量"，稳定感就丢了。

---

## 三、核心转向：内容变源真相，渲染变纯函数

不再追求"实时生成稳定报告"，改为：

1. **分析报告 = 一份被保存的草稿文档（槽位内容）**，是项目的一等公民。用户或 AI 辅助填好并**保存**后，它就是固定的"源真相"。
2. **"生成 / 导出报告" = 对这份已保存文档做纯函数渲染**（`export_from_text(saved_doc)`）。不重造内容，只排版。同一文档永远同一结果 = 稳定。
3. **AI 辅助 = 就地编辑这份文档的某个槽位**，改完用户确认 / 可撤销。AI 不再是"生成器"，而是"编辑器"。不保存就当没发生；保存了就冻结成真相。
4. **空槽位 = 显式"待补充"占位**（合约可见、不是 bug），绝不静默编造——正中你"禁止猜测事实"的红线。

### 和之前方案的本质区别

| | 之前（v1 / codex） | 现在（v2） |
|---|---|---|
| 内容来源 | 生成器（LLM/规则）实时产文本 | 作者（人 / AI 辅助）**先产出并保存**固定文档 |
| 导出动作 | 生成 + 渲染 + 后校验拦截 | 仅渲染（纯函数） |
| 同一输入的结果 | 每次不同（采样/素材漂移） | 永远相同（内容已冻结） |
| AI 角色 | 生成器（主力） | 编辑器（就地改单槽，可撤销） |

**区别只在一句话：内容是否被持久化并作为"源真相"。这是之前所有方案（含 codex）缺的那一环。**

---

## 四、落地（3 步，不动内核导出契约 `export_from_text`）

### 阶段 1 — 数据模型加"草稿文档"实体
- 把现在的 `task` + 实时生成结果，改成 `task` 持有 `draft_doc`（槽位 JSON 或 Markdown），可编辑、可版本化、可撤销。
- "生成"按钮**只触发渲染**，不再触发内容再生。
- 校验前移：必填槽位为空 → 拦下并提示补哪几个，**不渲染**（取代现在的"生成完再后校验"被动模式）。

### 阶段 2 — 前端改成"草稿工作台"
- 打开分析 = 编辑这份文档（槽位表单 / Markdown 双模视图）。
- "AI 帮我写这一格" = 调用 LLM 就地改写该槽，**等你确认**才落库。
- "导出" = 调内核渲染**已保存文档**。
- 彻底废掉 auto / rule / llm 三态路由的歧义（只留"手动"和"手动 + AI 辅助"）。

### 阶段 3 — 回归测试测"渲染确定性"
- 对同一份已保存 `draft_doc` 渲染两次，断言产物**字节一致**、章节齐全、无占位符、图存在。
- 这能真测稳定性，因为渲染是纯函数；而"测 LLM 今天心情"那种测试永远测不出稳定。

---

## 五、明确停做（之前一直在做、现在停）

- ❌ 继续指望"开 AI 生成整篇 / 逐槽"能稳定——只要内容是实时造的，就稳不了。
- ❌ 继续堆 spec / contract / prompt 约束生成器——治标，且 LLM 失败时报告直接没产出。
- ❌ 继续在 auto / rule / llm 路由上打转——歧义本身是不稳定来源之一。

---

## 六、预期结果

- **不开 AI**：人填草稿并保存 → 每次导出同一份高质量报告（内容是他自己定的，确定性渲染）。
- **开 AI 辅助**：只在草稿里就地扩写单槽，用户确认后才冻结；整体仍确定。
- **无论哪种**：同一份草稿 → 同一份报告。这就是你要的"稳定"。

---

## 附：为什么"方星海报告当黄金标尺"也不够

上一轮曾提"冻结方星海报告作黄金标杆"。思路对（要有可测量标杆），但**如果生成过程非确定，就永远无法稳定对齐标杆**——你量的是飘移的目标。v2 的做法是先把"内容"冻结成源真相，标杆才有意义：用方星海报告的**结构 / 章节 / 文风**作为草稿模板和渲染样式基准，而不是作为"让 LLM 模仿"的软提示。
